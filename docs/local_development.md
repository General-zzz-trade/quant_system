# 本地改进与部署准备

本阶段不需要本金、VPS 或 API 密钥。先验证执行与风控的故障行为，再验证策略的统计有效性。

## 现在就能运行

在仓库根目录运行，Python 3.11 及以上，无须安装第三方包或编译 Rust：

```powershell
python scripts/check_local_safety.py
```

这个命令测试生产代码中的订单生命周期、风控和启动参数，主动禁止网络连接，使用临时数据库并自动清理。成功退出码为 0，失败为 1。它不是回测或完整模拟交易，也不证明策略盈利。

完整系统使用 Python 3.12 和 Rust 扩展。Linux CI 另外运行适配器集成测试与原有核心测试；Windows 未安装完整 Rust/OpenSSL 构建工具链时，仍可先完成上述离线检查。

## 本批改动

| 原有问题 | 当前行为 |
|---|---|
| 未见成交时用意图数量生成 FillEvent | 仅接受订单号、交易对、方向匹配，且数量、价格有效的实际成交；按成交号去重 |
| 撤单失败仍按原数量追市价，部分成交可能重复开仓 | 单笔 post-only 入场，超时撤余单；无自动市价补单、拆单或盲目重试 |
| 下单超时不能区分“失败”和“已受理但响应丢失” | 请求前持久化预留记录，携带确定的 clOrdId，查询确认；未确认时锁住该品种新增敞口 |
| 每次重启重置日、周回撤起点 | SQLite 保存 UTC 日期、ISO 周、初始权益和已触发状态；周期内触发后不因权益反弹或重启解锁 |
| 风控异常、组合快照缺失仍放行 | 新开仓拒绝；平仓/只减仓保留执行路径 |
| 多 runner 各自使用独立额度计数 | 同一进程、同一账户共享组合风控和限流器 |
| 启动即直发订单、预挂单绕过风控、tick 伪造 K 线 | 移除这些路径；订单统一经过 ExecutionBridge，真实收盘 K 线进入策略 |
| 主程序默认可交易，dry-run 仍可能修改账户 | 默认 dry-run；移除直接清理零碎仓位；OKX dry-run 连接不设置杠杆 |

实际成交延迟可在运行期间每 5 秒重新查询。OKX 成交进入持久化消费流程：成交事实与待处理记录同时写入，消费状态与确认回执同时提交；完整历史暂未返回时继续保留开仓锁。恢复行为与验收方法见 [订单恢复说明](execution_recovery.md)。

OKX 订单/撤单语义依据[官方 API 文档](https://www.okx.com/docs-v5/en/#order-book-trading-trade-post-cancel-order)：撤单请求受理不等于已撤单，最终状态需要另行确认。数量仍在适配器内从合约张数换算成币数量。

## 以后连接模拟账户时

`runner.alpha_main` 的 dry-run 是“连接行情和账户、生成信号而不下单”，仍需要模型、数据、Rust 扩展和账户读取权限；没有这些条件时，使用前面的离线检查命令。

已有 systemd 服务不带 `--enable-execution` 时，现在只生成信号。这是有意的兼容性变化，不能仅通过重启服务恢复交易。

显式开启执行前，需要准备：

- `RISK_SCOPE`：稳定的账户与环境标识，如 `okx-demo-main`。模拟、实盘、不同子账户必须不同；同一账户重启保持不变。
- `DRAWDOWN_STATE_PATH`：默认 `data/runtime/drawdown.sqlite`。应放在持久磁盘或容器挂载目录。
- `ORDER_JOURNAL_PATH`：默认 `data/runtime/orders.sqlite`，同样需要持久化。
- 新鲜、完整的 `data/runtime/portfolio_risk.json`，由现有组合风险监控产生；缺失或超过有效期会阻止入场。
- `MAX_DAILY_DRAWDOWN_PCT` / `MAX_WEEKLY_DRAWDOWN_PCT`：默认 3 / 10。使用首次实际观测的账户总权益（含未实现盈亏），不冒称是午夜权益；入出金尚未自动校正。

启动时必须先成功刷新权益；之后每约 60 秒更新，超过 120 秒未刷新会拒绝新增敞口。跨 UTC 日/周需要新观测才能建立该周期基准。手动 kill switch 和策略暂停也只拦新增敞口，不丢弃行情或成交事实。

## 尚未完成，不能当作实盘验收通过

1. **恢复边界**：新版本 OKX 订单已支持父事件恢复、持久化成交去重、待处理成交重放及状态/回执原子提交。旧数据库缺失方向、父事件的历史订单继续锁住，不能猜测归属；人工订单、对冲持仓、缺失或超出接口窗口的成交仍需单独对账。不要删库或改 RISK_SCOPE 绕过。
2. **策略与账务验证**：执行模式下的实际仓位和入场均价改为成交驱动，部分平仓保留余仓，反向开仓等待平仓确认；4h 信号模式保留独立信号状态。仍需完整历史回放验证策略行为变化，以及资金费、入出金、跨币种费用与账户总权益对账。
3. **其他交易所**：本批订单确认重构针对 OKX；Bybit/Binance 需要同等级的故障测试及适配，不能由 OKX 测试结果推断通过。
4. **组合敞口**：同机同数据库目录、同 RISK_SCOPE 的 OKX 执行进程有单写者锁，多个 runner 在进程内运行。此锁不是跨主机分布式额度账本；组合文件也未包含全部在途订单额度。部署前仍需统一预留与释放。
5. **模型验证**：重新划分训练、调参与最终测试集；修复 4h/1h 时间对齐；验证线上特征时效和与离线特征的一致性；计入费率、滑点和资金费。历史 README 中高收益与“无前视偏差”尚未重新验收。
6. **持续模拟**：完成上述问题后，在本地回放和模拟账户记录连续运行、断网、重启、拒单、延迟成交的可复现结果，再讨论 VPS 和小额实盘。
