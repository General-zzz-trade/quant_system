# ADR-0016：M5 运行就绪：告警出口、启动告警、心跳、重启策略、单一执行进程、备份与恢复、通过标准

- 日期：2026-11-15
- 回答路线图第 6 节第 9 项：主网没有告警出口时是否拒绝启动。

## 背景

【代码】

- 告警出口：
  - 两个变量都不设时只写进程日志（`trading/infrastructure/settings.py:73-82`）；
  - 发送失败被吞掉，调用方无法知道是否送达（`trading/adapters/notify/telegram.py:73-81`）。
- 心跳：没有。看门狗与运行时在同一台主机上（`infra/systemd/health-watchdog.timer`），主机宕机时两者一起失联。
- 重启：唯一的服务单元是模拟盘，带 `Restart=on-failure`、`RestartSec=60`（`infra/systemd/binance-target.service:16-18`）。项目规则禁止自动重启实盘服务（`CLAUDE.md` "No automatic risk escalation or restarts"）。
- 备份：没有。
- R20：执行租约按状态目录加锁，键是 `sha256(RISK_SCOPE)`（`trading/adapters/files/lease.py:15`），锁文件在订单库旁边。
  - 同一账户可以在两个目录各起一个执行进程。
  - 两个不同的 `RISK_SCOPE` 用同一把 API Key 时，也能并行。
  - 手工工具用同一把租约，保证运行时在跑时它们拒绝执行（`trading/infrastructure/manual.py:202`）。
  - 已知缺陷测试：`tests/characterization/test_risk_state.py:125`。

## 决定

1. **告警出口（决定 D）**：执行模式（测试网和主网）缺 `TELEGRAM_BOT_TOKEN` 或 `TELEGRAM_CHAT_ID` 任何一个，都拒绝启动。检查在连接账户之前做。模拟盘可以只写日志。
2. **启动告警（决定 J）**：
   - `Notifier` 端口新增 `deliver(title, detail, *, timeout_s) -> bool`：同步发送，确认送达才返回真。
   - 本地检查全部通过之后、连接账户之前，发送"执行模式正在启动"（含账户身份和网络，不含密钥）。没有确认送达就拒绝启动，不发出任何账户请求。超时按失败处理。
   - 账户检查（ADR-0010）若拒绝启动，再发一条"拒绝启动：原因"（尽力发送）。
3. **心跳（决定 F、K）**：
   - 新端口 `Heartbeat.beat()`；执行模式必须配置 `HEARTBEAT_URL`，否则拒绝启动。
   - 每分钟最多发一次，在后台发送、带超时。预热和等待行情期间也照常发送，免得误报失联（审计 L6）。
   - 运行中发送失败只记日志，从不影响交易和平仓：心跳只是旁观者。
   - 心跳地址在配置日志里按密钥处理，不写出来。
4. **重启策略（决定 E）**，分三个单元：
   - 模拟盘：保持现状。
   - 测试网执行：
     - `[Service] Restart=on-failure`、`RestartSec=60`；
     - `[Unit] StartLimitIntervalSec=3600`、`StartLimitBurst=3`、`OnFailure=quant-alert@%n.service`。
   - 主网执行：`Restart=no`、`OnFailure=quant-alert@%n.service`。由人确认后手动启动。
   - systemd 的语义（审计 L1，按主机上 systemd 255 的手册）：
     - `OnFailure=` 在每次失败时都触发，包括随后被自动重启的那次，所以每次失败都有一条告警；
     - `StartLimitBurst` 把人手动启动也算进去。演练前后执行 `systemctl reset-failed`，运行手册写明。
   - 每次启动都重新走全部启动检查：规格、门槛、状态目录、主机锁、本 ADR 第 1–3 条、ADR-0010。
5. **单一执行进程（R20，本设计的建议）**：
   - **账户身份** = `sha256(网络 + ":" + API Key)`，只用 Key，不用私钥。
   - 主机级锁：锁文件放在固定的主机目录（`/var/lib/quant/locks/<身份>.lock`），与状态目录无关。
   - 运行时、手工工具（`manual`）、恢复命令（`state_dir restore`）都用这把锁：运行时在跑时，后两者一定拒绝。
   - 锁目录由 `state_dir init` 创建（由人执行）。锁目录不存在或不可写时拒绝启动。
   - 跨主机无法由本机阻止。运行手册写明"一个账户身份只在一台主机上运行"。
6. **状态备份与恢复（决定 G、M）**：
   - 备份：
     - `state-backup.timer` 每小时用 SQLite 在线备份接口给 `state.sqlite` 拍快照；
     - 写完后校验：能打开、版本号对、表齐全；保留 14 天，失败时告警。
     - **急停文件不备份**：只有急停命令写它（K4）。
   - 恢复：`state_dir restore` 只在状态库丢失或损坏（启动检查拒绝它）时允许。要求：
     - 拿得到主机锁（运行时已停止）；
     - 写明理由、键入确认，并留审计记录。
   - 恢复后一律收紧：
     - 当期回撤视为已锁定，到下一个周期边界才按规则解除；
     - 当日下单计数视为用完；
     - 所有品种暂停入场，由人逐个解除；
     - 急停文件保持原样，不做任何改动。
   - 恢复后的首次启动照常走全部启动检查。ADR-0010 会发现与交易所的不一致，并拒绝启动。
7. **M5 通过标准（决定 I）**：
   - 连续 4 周对账无差异、没有未解释的告警；
   - 7 类演练各至少一次并有记录：急停平仓、回撤锁定、止损触发、重启恢复、备份恢复、告警送达、心跳失联；
   - 出现任何差异都从头计时；往测试网主机部署资金路径的改动也从头计时。

## 状态未知与失败方向

- 第 1、2、3、5 条在启动时失败即关闭：拒绝启动，不连账户，不建运行时。
- 心跳在运行中失败时放行：旁观者的故障不应该变成交易故障。
- 备份失败不影响运行时，只告警。
- 恢复只会让风险状态变严，不会变松。与交易所的任何不一致都由 ADR-0010 拒绝启动。

## 备选方案

- **告警**：只有主网强制；或者都不强制。技术负责人选了执行模式一律强制。
- **重启**：都不自动重启；或者都有限次重启（后者要修改项目规则）。技术负责人选了只有测试网有限次重启。
- **心跳**：在第二台主机上运行看门狗（需要第二台机器）；或者只用本机看门狗。
- **恢复**：风险状态取恢复前和快照里更严的一方；或者原样恢复（审计 M1 指出会放宽风险状态）。技术负责人选了只在丢失时恢复、恢复后一律收紧。
- **R20**：在交易所侧做标记，例如客户端订单号里带进程标识、启动时检查。只能事后发现，不能事前阻止。

## 后果

- 执行模式的前置配置变多：Telegram 两个变量、心跳地址、锁目录。
- Telegram 自身故障时无法启动执行模式；模拟盘不受影响。
- 主网异常退出后需要人介入；在此期间，交易所侧止损仍然有效。
- 恢复备份之后，策略在人逐个解除暂停之前不会入场。

## 验收

- 启动检查的新测试：
  - 执行模式缺告警配置、启动告警没送达、缺心跳地址、锁目录不可写，各自拒绝启动，并且账户请求数为 0；
  - 模拟盘缺这些配置照常启动。
- 心跳：
  - 注入一个总是失败的心跳，平仓和对账照常；
  - 预热期间也发心跳；
  - 配置日志里没有心跳地址。
- R20：
  - 已知缺陷测试改为断言"同一身份的第二个进程被拒绝"（行为改变，按本 ADR 记录）；
  - 两个 `RISK_SCOPE` 用同一把 Key 时，第二个被拒绝；
  - 运行时在跑时，手工工具和恢复命令拒绝执行。
- 单元文件检查：主网单元是 `Restart=no`；测试网单元的 `StartLimit*` 写在 `[Unit]` 里。
- 备份与恢复：
  - 快照能被启动检查接受；
  - 状态库完好时，恢复命令拒绝；
  - 恢复后回撤锁定、计数用完、所有品种暂停，急停文件没有被改动；
  - 加强现有的"只有急停命令写急停文件"测试，让它也能发现复制文件这种写法（审计 M1）。

## 实施更正（2026-11-16，S6–S8 审计之后）

- **恢复后回撤锁定的后果**（审计中 1，技术负责人 2026-11-16 决定保持锁定并写明）：在本系统里回撤锁定会让下次启动按市价平掉所有仓位，并且空仓到本 ISO 周结束（最长 7 天）。"后果"一节原来只写了"不会入场"。恢复命令的提示和结果、运行手册、M5 核对清单都写明了这一点；M5 的备份恢复演练会真的平仓。
- **库检查读全部页**（审计中 4）：启动检查、备份对源库和快照的检查、恢复的"丢失或损坏"判断，都加了 SQLite 的 `quick_check`。原来只看版本号和表清单，数据页损坏时照样通过。
- **恢复把损坏的库整套移开**（审计中 3、低 1、低 7）：连同它的 `-wal`、`-shm`、`-journal` 一起移进 `state.sqlite.broken-<时间>/`，再把快照放进来。留在原处的 WAL 或热回滚日志会被应用到新库上（审计员实测：锁定被悄悄撤销）。
- **当天计数用完与配置无关**（审计低 2）：原来按运行恢复命令的那个 shell 的限额写，服务的限额更高时计数并没有用完；现在写一个远超任何配置的数。
