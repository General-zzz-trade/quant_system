# ADR-0015：策略端口与多策略承载（只定接口，判定通过后实现）

- 状态：**已批准**（2026-11-15，技术负责人"现在全部批准"）。原为提议稿；下面的内容是批准时的版本，实施中如有变动在本文更正并记入 `execution-log.md`。
- 日期：2026-11-15

## 背景

三个前向候选的形态【代码 `research/results/forward_candidates_2026-11-14/*.json`】：

| 候选 | 交易形态 | 决策节拍 | 需要的输入 |
|---|---|---|---|
| A `pair_ridge_pd_7d` | ETH/BTC 配对，两条腿 | 每 7 天 | 价格、资金费、溢价、持仓量、主动买卖量（19 个特征） |
| B `dir_ridge_7d` | 单品种，可空 | 每 7 天 | 同类 15 个特征 |
| C `flush_reversal_72h` | 单品种，只做多，持有 72 小时 | 事件触发 | 持仓量等指标，分位数窗口 8,760 小时 |

现在的运行时【代码】：

- 会话一个品种一个，目标由写死的 `latest_target` 计算（`trading/application/session.py:103-105`）。
- 入口只接受一种规格（`runner/binance_target.py:61`）。
- 行情端口只有 K 线和资金费（`trading/application/ports.py` 的 `MarketData`）。
- 再平衡支持空头和换向（`trading/domain/rebalance.py:47-52`）。

前向协议规定，候选判定"继续合格"后才可以开始做它的运行时，配对需要新的两条腿运行时【代码 `research/protocols/2026-11-14-forward-candidates.md:129`】。

## 决定（接口草案，现在不实现）

1. **策略端口**：
   ```python
   class TargetModel(Protocol):
       name: str
       def inputs(self) -> InputSpec: ...            # 需要哪些行情序列、多长的历史
       def target(self, data: MarketInputs, now_ms: int) -> Target: ...   # Target(weights: Mapping[str, float], ready: bool)
   ```
   - 单品种策略返回一个品种的权重；配对策略同时返回两条腿的权重。
   - 决策节拍（每 7 天、事件触发）在模型内部处理，会话每根 K 线照常询问。
2. **衍生品行情端口**：`DerivativesData`，提供溢价、持仓量、主动买卖量。候选 C 需要的 1 年历史超出交易所接口的保存期限【推测：持仓量历史接口只保留约 30 天】，所以需要本地指标存储加增量下载（复用 `data/downloads` 的快照机制）。
3. **两条腿协调**（只针对候选 A）：
   - 同一决策的两条意图共享一个"组"编号；
   - 一条腿成交、另一条腿失败时，按"先补齐、补不齐就把已成交的腿平掉"处理，并告警；
   - 配对级回撤和配对级止损由组合层负责。
4. **组合层**：
   - Binance 单向持仓模式下，一个品种只有一个净持仓。
   - 多个策略同时运行时，由组合层把各策略的目标净额成每个品种的一个目标，再交给现有的会话和再平衡。
   - 3 倍敞口上限不变，按账户总敞口计算。

## 状态未知与失败方向（实现时适用）

- 任何一条腿的状态未知：整组不再新增敞口，只允许减仓。
- 衍生品行情缺失或过期：该策略的目标为"未就绪"，不入场，已有仓位按 ADR-0005 处理。

## 备选方案

- **现在就实现策略可插拔**：会占用 M5 前后的工程时间，而候选可能不通过判定。技术负责人没有选。
- **一个品种只归一个策略**：比组合层简单，但配对策略和单品种策略在 BTC、ETH 上一定会冲突。

## 后果

- M5 不受影响。
- 判定通过后，配对候选的工作量最大：需要两条腿协调、配对级风控、衍生品行情和本地指标存储。

## 验收（实现时）

- 每个候选的运行时都要有"纸面与研究逐笔一致"的测试，作为门禁。
- 两条腿协调要有"一条腿失败"的场景测试。
